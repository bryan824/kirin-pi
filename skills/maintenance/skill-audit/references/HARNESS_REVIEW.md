# Harness Review

Reassess the whole harness when a model, host capability, upstream change or
recurring failure challenges its design. Start from useful outcomes, not the
current file layout. A stronger model can need less scaffolding, but its release
alone proves no improvement.

## Frame the review

Establish purpose, constraints and scope. Protect core features and quality, not
every helper, option or minor feature. Propose retiring low-value behavior when a
model or simpler design covers it. Default to propose, then apply after approval;
source work does not authorize installation, upgrades, global configuration or
publication. A no-change result is valid.

Choose the strongest available review model the user wants from the current host
registry. Pin its exact provider/model and thinking level, and check actual resolved
model/context: presets and host overrides can defeat an intended selection. When
delegation is authorized, use fresh read-only reviewers on that selected model;
otherwise disclose self-review. A failed path remains blocked, not permission to
switch models, runners or take over a failed child.

Identify the complete candidate: revision plus staged, unstaged and new content,
including pre-existing work. A commit alone does not identify a dirty tree. Keep a
diff/content digest or snapshot in the existing ignored record when comparison or
resumption needs it. Record actual host/tool versions and loaded source paths;
checkout sources, installed copies and effective runtime resources are different.

Whole-harness reassessment includes bounded official host release/doc checks, not
a private-history scan or a sweep of other upstreams. Explicit source absorption
uses [Upstream review](UPSTREAM_REVIEW.md) for selection, ranges, licensing and
checkpoints. A local review does not advance that ledger.

## Prefer both hosts' native harnesses

On every whole-harness reassessment, check the latest stable **Pi and Claude Code**,
even when a model triggered it. Identify latest stable and installed versions
separately. Use official changelogs, relevant docs, supported APIs/configuration and
safe observations of actual behavior—not release headlines alone. Source pointers
belong in the upstream ledger; previews need a separate request.

Compare native instructions/memory, skills, tools, permissions, planning/delegation,
sessions and UI with Kirin's actual consumers. For each relevant change, identify
what the host supplies, which custom behavior it can improve or replace, supported
and installed availability, and evidence or gaps. Prefer native ownership when it
preserves useful outcomes; adopt no feature merely to tick a box. Required upgrades
or compatibility changes are separate proposals, never automatic installation.
Missing release/capability evidence is an explicit coverage gap, not a completed
assessment or permission to advance a checkpoint.

## Challenge the whole shape

Run the isolated source analyzer with explicit roots and no logs unless those are
in scope. Then inspect real consumers and checks. Use one working coverage table:
surface/paths, evidence, judgment, and covered/blocked/excluded with a reason. A
listing is not inspection, and unreviewed layers cannot disappear from the verdict.

| Surface | Question |
|---|---|
| Purpose and architecture | What is the smallest harness meeting today's real needs? |
| Skills, references and startup instructions | What improves this model's tasks rather than repeating competence or adding ceremony? |
| Agents and routing | Which distinct roles earn their place, and how do model/context/tools actually resolve? |
| Extensions, hooks and tools | What stateful behavior remains necessary after native replacements? |
| Workflows and authority | Can bounded work proceed, consequential choices reach the user, and failures stay visible? |
| Setup and package surface | Are source, installation and runtime ownership separate, with unrelated work preserved? |
| Docs, memory and provenance | Does current truth have one owner, private records stay private, and borrowing remain honest? |
| Tests and behavior | Which checks catch real regressions rather than pinning prose or certifying unexercised behavior? |

Use `SKILL.md`'s layer criteria. Consider a target architecture before polishing
files; use `architecture` or `write-skill` when available for their respective
questions. Missing siblings do not require installation: state the target and
assumptions, or use sharp triggers, reachable references and preserved boundaries.

Prefer deletion, an existing owner or native behavior over a new component. Map
valuable behavior from removals to a replacement or an explicitly proposed
retirement. Missing usage is not disuse; source size is not loaded-context cost;
a shorter prompt is not necessarily better.

## Propose, compare and verify

Give findings with evidence, impact, owning paths and disposition: keep/already
covered, simplify/absorb, replace/delete, or defer/exclude with a revisit trigger.
Resolve conflicting recommendations into one plan covering preserved/retired
behavior, compatibility, verification, gaps and rollback. Obtain approval before
source or ledger edits; amend material changes rather than silently changing scope.

Use [Behavior probes](BEHAVIOR_PROBES.md) for repeatable inputs and observable traces.
Keep comparison axes separate:

- **Model change:** same harness, tasks, tools and surrounding instructions; old
  versus selected model. If old evidence is unavailable, establish a new baseline
  and state that no model comparison occurred.
- **Harness change:** same selected model/environment; frozen before versus
  candidate source. Changing model and harness together cannot isolate either.

Run relevant bounded cases when authorized; repeat consequential or inconsistent
results within the agreed budget. Judge decisions and tool traces, not a model's
self-score. Report regressions, unavailable evidence and stochastic limits. A small
sample is a baseline, not universal superiority; keep deterministic integration
checks and add representative real tasks for a redesign.

Apply approved changes with one writer per shared boundary. Verify the complete
candidate against requirements, rerun affected checks and packaging, and recheck
coverage and preserved behavior. Required missing evidence blocks a pass; explicitly
accepted non-blocking risks stay visible. Only fully reviewed, approved upstream
checkpoints can advance, preserving borrowing origins.

Return model/candidate identities, layer/source coverage, dispositions, changes,
observed/static/unrun evidence and remaining decisions. Keep useful receipts in the
existing ignored record, not a review diary, task store, model picker or scheduler.
Stop when requirements are met and no evidence-backed useful change remains, not
when every file has changed.
