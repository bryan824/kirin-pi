# Skill Style

## What earns context

A skill supplies a stance, a known failure mode, an otherwise invisible local
standard, or a boundary to neighboring work. It should not reteach ordinary
competence. One mindset is a useful ownership test, not a reason to invent a skill
for every noun or phase.

Assess wording relative to the actual models and tasks. A line that seems obvious
may preserve a real boundary; a fashionable instruction may do nothing. Before
cutting, identify the behavior and whether it survives in the owner, a reference,
or an explicitly approved retirement. Do not optimize character count by losing
the purpose of the instruction.

## Discovery and progressive disclosure

When selected and exposed by the host, names/descriptions help choose relevant
skills; bodies and references load separately. File presence is not selection,
selection is not a read, and a read does not prove the complete body is retained.
Inherited context, repeated injection, tools and external extensions have their
own costs. A filesystem analyzer cannot reconstruct all of those surfaces.

Write each pointer for its job. State when to load the referenced material and
what question it answers. Place long details, examples and schemas in references
when they are conditional, not to pretend their tokens disappear. A broad
mandatory link can cost as much as inline text once read; copied references add
maintenance drift as well as payload.

Resolve paths from the loaded skill's directory. Keep necessary material inside
that selected skill. Shared sibling owners must be optional with a focused
fallback when absent; do not silently install siblings or copy an entire review
framework to work around a missing file.

## Shape follows the failure

A short stance, a few consequential principles and a useful carry-forward usually
suffice. They are not required headers or numerical quotas.

- Use a situation-first description with discriminating nouns. Generic verbs and
  long synonym lists can blur neighboring triggers.
- State the desired behavior plainly. Use a conditional for a context-dependent
  choice, and explicit authorization for side effects. A prohibition can be
  appropriate for a genuine safety boundary; neither negative nor positive wording
  is a universal model law.
- Sequence steps when ordering is causal, such as reproducing before choosing a
  fix. Let the model organize ordinary work. Avoid compulsory fanout, retry
  quotas, magic approval words and one-session-per-unit rituals.
- Name observable outcomes rather than output ceremony. Keep a rigid format when
  another consumer really parses it; otherwise let the answer fit the problem.
- Co-locate a concept with its caveats. A coined metaphor that needs explanation
  is rarely cheaper than the direct instruction. Familiar leading words can be
  useful, but reliable invocation/execution must be evaluated, not asserted from
  pretraining folklore.

## Choose an owner

First try an existing principle, then a reference, then an existing component. A
new owner is the last resort and must represent a missing capability or mindset.
For a mechanically detectable failure, inspect the repository's existing checks
before writing another instruction. Repair or extend the cheapest suitable check;
reserve prose for judgment, rationale and non-obvious boundaries. A checker does
not remove the need to tell an agent when to run it or grant installation authority.

- Skills carry reasoning and posture.
- Extensions/hooks own justified commands, lifecycle or enforcement not already
  supplied by the native host. Do not duplicate the host's loader or orchestration.
- Current repository docs hold stable contracts and reasons not recoverable by a
  cheap environment lookup. A document repeating configuration is a cache that
  needs an owner or deletion.
- Working records preserve evidence and continuity when needed; they are not an
  excuse for another task store or a new file per question.

The optional memory protocol lives with the `project-memory` skill in its
`PROJECT_MEMORY.md`, not in this references directory. Follow existing repository
memory conventions when that sibling is absent. Read-only work proposes changes;
only an authorized writer updates durable truth.

Shared process can belong in an existing skill when several real callers need the
same judgment. A few lines of posture belong in one principle or reference, not a
new orchestrator. An inline skill read does not clear preceding context; splitting
files alone is not isolation.

## Native invocation is not containment

Kirin targets Pi and Claude Code with portable skill metadata. Keep host-specific
implementation in the appropriate integration, not a second prompt hierarchy.
Use supported fields; do not infer enforcement from an unknown field's presence.

`disable-model-invocation` controls discovery/automatic entry according to the
host. It does not revoke filesystem reads or replace actual permissions. A body
gate can protect an action, but neither it nor a hidden description is a sandbox.
Use user-only entry for genuinely hand-driven work, and separate task approval
from commit, publication, installation or destructive-operation authority.

Effective discovery depends on current host version, trust, configured resources,
collisions and overrides. Do not impose a universal project/package/personal
precedence, assume every package file is loaded, or claim a native truncation
algorithm from a guessed budget. Consult the actual host inventory when available;
otherwise report the limitation.

## Evaluation and cleanup

Inspect coverage before arguing from counts. No observed usage can mean a missing
root, stale copy, filtered or partial logs, an unsupported tool, or inherited
context—not a useless skill. Exact content differences matter; high word overlap
can hide a changed permission or negation.

Static contracts catch bad metadata, broken paths and accidental surface changes.
They do not prove a model follows the guidance. Authorized behavioral evaluation
needs representative tasks, observable outcomes, a suitable comparison and honest
failure reporting. Keep source-size estimates, loaded context, price and latency
separate. A few successful runs do not establish universal reliability.

Look for stale layers, sprawling scope, duplicated obligations, premature
completion and no-op guidance. Correct the causal ownership or wording problem;
adding a stronger adjective is not evidence of a fix. Preserve trigger nouns and
non-obvious boundaries during compression. Require authority for cleanup and
leave deployed/user-owned copies untouched unless explicitly included. A clean
local audit with no durable correction writes nothing.
